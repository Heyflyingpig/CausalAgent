01 · Executive summary

先讲设计原则，再讲实现细节

整个阶段一可以用三个动词概括：监控数据“采下来再共享”，业务数据“有界地现查”， 高风险动作“预览后原子写入”。这三条链路共用同一套后端授权和数据库访问分层。

01

观测：采集与展示解耦

独立 monitor 按不同周期读取 MySQL，把标准化结果写进共享快照。 看板 GET 只读最近快照，手动刷新也只登记请求。

02

查询：真实数据但必须有界

用户、会话、任务、文件等明细通过明确 DTO、游标分页和正文分块从主库读取， 没有通用表浏览器，也没有任意 SQL。

03

写入：副作用形成闭环

CSRF、重新认证、影响预览、明确确认、幂等键、稳定锁顺序、业务变更与审计 在主库事务里形成完整闭环。

会议开场建议： 不要从 Vue 页面讲起。先说明数据库压力和一致性风险分别来自哪里，再说明为什么需要三条链路； 前端只是把后端已经冻结的安全语义可视化。

02 · System architecture

同一个管理后台，背后不是同一种数据库访问

点击下方按钮可以突出某一条链路。最重要的区别是：监控看板读取共享快照， 业务明细读取真实表，高风险操作只走主库短事务。

03 · Data acquisition

MySQL 的值来自四类事实源，再统一成可解释结果

看板不是从一个大 SQL 得到所有数据，而是针对不同事实使用不同查询入口。 每个结果都带来源、采集时间、状态和估算标识，前端不会把“估算”和“强一致事实”混在一起。

运行状态与主从事实

读取连接、版本、时间、慢查询累计值和复制线程状态。

  • SHOW GLOBAL STATUS：连接数、运行线程、慢查询累计值
  • SHOW GLOBAL VARIABLES：连接上限、slow query 配置
  • SHOW REPLICA STATUS：专用观测账号读取，2 秒缓存
  • VERSION() / UTC_TIMESTAMP(6)：实例事实与统一时间

Schema、revision 与容量

核对仓库期望和实例事实，容量允许使用副本估算。

  • alembic_version 对比仓库 head
  • information_schema 读取表、列、索引、外键
  • 容量最多返回 200 张表，并明确 is_estimate=true
  • 关键约束由 metadata 检查代替重复全表孤立扫描

SQL 性能摘要

摘要含义是“高负载 SQL”，并非逐条慢查询日志。

  • performance_schema.events_statements_summary_by_digest
  • 按累计 SUM_TIMER_WAIT 降序，默认 20、硬上限 100
  • 慢查询告警用同一实例、同一累计计数的采集窗口增量
  • 实例 UUID 只保存散列后的来源标识，不暴露真实主机

真实业务记录

用户、会话、任务、事件和文件不走快照，而是经有界 API 现查。

  • 列表默认 20、最多 50，使用稳定排序的不透明游标
  • 正文仅在明确点击后按最多 64 KiB 源字节分块读取
  • CSV 预览限制 256 KiB、100 行、50 列、单元格 1000 字符
  • DTO 不返回密码哈希、BLOB、连接信息或完整秘密字段

04 · Load control

降低数据库压力靠的是“减少频率 × 限制范围 × 隔离执行”

不是简单地把所有 SELECT 扔给从库。真正的降压来自共享快照、分层周期、有界查询、 渐进读取、缓存和有限连接池；副本只承接明确允许短暂延迟的路径。

05 · Authorization

权限不是一个 role 字段，而是应用层与数据库层的双重收口

浏览器路由只改善体验，不构成授权依据。每个管理请求都会回到后端， 再从主库确认真实角色、启用状态和认证版本；高风险写入还要跨过额外安全门。

APP 01

登录与 Session 恢复

主库强一致读取 role、is_active、auth_version，Session 不是最终事实源。

APP 02

统一管理员授权

admin_required 复用在页面和全部管理 API；未登录 401，普通用户 403。

APP 03

写入安全门

Session CSRF、当前管理员密码再认证、影响预览、明确确认、批量上限与 request ID。

APP 04

权限变化立即失效

角色、状态或密码实际变化时递增 auth_version，目标用户旧 Cookie Session 随即失效。

职责账号 允许做什么 明确不做什么 失效策略
MYSQL_WRITE_USER 主库业务写、Alembic、readiness 前端不直连；后台不暴露通用 SQL/DDL 连接失败直接报错，不自动切主
MYSQL_READ_USER 主/从业务 SELECT、单表 Digest SELECT 不执行复制状态查询，不获得全局 SELECT 副本异常时回退主库读池
MYSQL_REPLICA_STATUS_USER 复制状态观测 不读业务表，不写业务数据 不可用即判定副本不适合读
MYSQL_REPLICATION_USER 复制通道拉取 binlog 不参与 Flask / worker / monitor 查询 复制异常只告警和回退，不自动故障切换

准确边界：当前写账号同时承担应用写入与迁移所需 DDL 权限，这是阶段一的真实配置， 还不是“运行账号与 migrator 完全拆分”。安全收口依赖后端没有任意 SQL/迁移入口，以及所有业务写都进入固定 service。

06 · Concurrency control

锁竞争不是“少用锁”，而是选对锁、缩短等待、固定顺序

不同并发问题使用不同机制：监控采集用非阻塞命名锁，任务领取用 SKIP LOCKED，配置保存用乐观版本，高风险写入用稳定行锁顺序和幂等重试。

同类采集只能有一个赢家，拿不到就立即退出

锁名包含快照类型，例如 causalchat:db-monitor:realtime。 因此不同类型可以并行，同一类型跨多个 monitor 实例只执行一次。

计算到期快照先读一次调度状态，不为未到期项目加锁。
GET_LOCK(key, 0)超时为 0，竞争失败不等待、不堆积。
拿锁后再次复核 due避免排队期间已有其他实例完成采集。
持久化并释放连接级锁结果写入共享快照，最终块始终尝试 RELEASE_LOCK。
结果：页面刷新、多个 monitor、定时任务不会重复触发同一类重采集。

稳定锁顺序，把不可避免的行锁变成可预测的短事务

高风险管理员事务固定使用 READ COMMITTED，锁等待默认 5 秒； 目标用户按 ID 排序锁定，降低不同批次反向拿锁造成死锁的概率。

锁操作者并在事务内再认证防止事务开始前后角色或密码状态发生变化。
锁全部启用管理员串行保护“至少保留一个启用管理员”规则。
按稳定 ID 锁目标批量操作和用户删除遵循相同顺序。
锁子记录并重新核对阻断条件活动 job、删除规模、确认值均在锁内重算。
业务变更、操作记录、审计一起提交任一步失败全部回滚。
锁超时或死锁返回 transaction_retryable，调用方必须复用原幂等键重试。

Worker slot 使用 FOR UPDATE SKIP LOCKED

多个 slot 抢任务时，不等待已被其他 slot 锁定的行，而是跳过并寻找下一条可执行任务。 领取事务只包含“选中 + 状态推进”，随后立即提交。

按 queued 优先、created_at 排序形成稳定领取顺序。
LIMIT 1 + SKIP LOCKED多个 slot 不会争抢同一行后互相等待。
原子推进 running写入 worker、locked_at、heartbeat 和 attempt_count。
提交后执行长任务Agent/MCP/RAG 执行期间不持有领取行锁。
同一用户 + 会话的活动任务再由 active_session_key 唯一键兜底并发创建。

把“重试”转化为数据库可判定的同一操作

仅靠应用判断无法覆盖并发竞态，所以关键路径都落到唯一约束； 相同请求重放原结果，同键异参明确冲突。

管理员操作(actor_user_id, idempotency_key) 唯一；请求正文以服务端 HMAC 指纹区分。
活动分析任务active_session_key 唯一，第二个并发创建回读已有 job。
checkpoint pending writes完整业务键做 SHA-256 BINARY(32) 摘要后建唯一索引。
监控配置版本号 + 行锁；旧版本保存返回冲突，不做静默覆盖。
特殊 pending write 使用 upsert，普通 write 使用 insert-ignore；不会因任务重试重复累积。

07 · Consistency matrix

不是所有 SELECT 都去从库：一致性按业务风险分配

这张表是解释主从设计最关键的材料。原则是：安全决策和实时顺序固定强一致； 只有历史列表和容量估算这类允许短暂延迟的路径才尝试副本。

数据路径 一致性 为什么 失败时
登录、Session 恢复、管理员授权 strong 角色、启用状态、认证版本不能读旧值 主库不可用则拒绝，不从副本猜权限
管理列表、敏感详情、写前预览 strong 管理员必须看到刚提交的精确结果 返回稳定错误与 request ID
普通历史列表、表容量估算 eventual 允许短暂延迟，并显式标记来源/估算 副本异常、延迟未知或超阈值即回退主库
Job 创建/领取/心跳/终态、SSE 事件 strong write 不能因复制延迟重复领取或漏读实时事件 事务失败回滚，事件续传按主库 ID
用户/文件写入、访问计数、checkpoint primary write 参与事务、幂等、生命周期或顺序语义 不自动切主，明确失败
deep 审计 manual strong 范围广但低频，永不自动调度，不自动修复 单项超时/失败降级，不阻塞其他快照
连接容量口径

每个 OS 进程的池上限是 write_pool + read_pool × (1 + replica_count)。 默认一主一从为 5 + 5 × 2 = 15。 一个 Web 进程、一个 worker 进程和一个 monitor 进程理论共 45 个池连接； worker slot 共享所在进程的池，不按 slot 数再次相乘。

2026-07-27 的非生产只读快照记录：max_connections=151、 Max_used_connections=31、Threads_connected=31、 Threads_running=3。该数据会漂移，发布前必须重新测量。
