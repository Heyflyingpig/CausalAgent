## 一、结论与执行边界

阶段一继续聚焦“数据库管理”，但拆成三个可以独立验收、风险逐步增加的交付块：

| 交付块 | 核心目标 | 数据库权限边界 | 前端要求 |
|---|---|---|---|
| 第一块：只读事实与 MVP 看板 | 把代码推断和实例真实状态分开，建立可重复执行的数据库事实报告 | 只允许 `SELECT`、`SHOW`、`information_schema`、`performance_schema` 等只读查询；禁止 DDL、DML、迁移和自动修复 | 一个能看懂状态、表格和告警的单页看板即可 |
| 第二块：受控写操作 | 在管理员权限、事务和迁移门禁下，引入明确且有限的数据库写操作 | 只允许预定义业务操作；全部写主库；禁止任意 SQL 控制台 | 在同一 MVP 看板增加少量管理入口，不追求完整后台设计 |
| 第三块：治理完善与阶段收口 | 补齐数据生命周期、约束、性能、主从、测试和发布流程 | 保留最小权限；高风险修复只通过专用脚本和人工确认执行 | 完善错误态、空态、分页和基本可用性，不做视觉大改版 |

阶段一的完成标准不是“做出一个漂亮的数据库后台”，而是：数据库事实可信、只读与写入边界清楚、受控操作安全、关键数据关系可验证，并为后续日志管理和并发安全提供可靠基础。

### 1.1 本计划采用的架构口径

- 保留当前 Flask、Python worker、MySQL、Alembic 架构。
- Alembic 继续作为唯一的业务 schema 变更入口。
- `Database/database_init.py` 继续只负责确保数据库存在和检查连接，不恢复建表职责。
- 第一版只有普通用户和管理员，不引入租户、角色表、权限表或完整 RBAC。
- 阶段一前端继续使用 Flask 静态资源，不新建 Vue、Vite、React、Spring Boot 或 TypeScript 工程。
- 不修改已有 Alembic migration；所有结构变化都通过新的 migration 追加。
- 数据库阶段只预留第三阶段必需的租约、幂等和状态约束，不提前启用新的 worker 并发协议。

### 1.2 明确不在阶段一范围内

- 任意 SQL、建表、删表、改表或 `DROP` 控制台。
- 在 Web 页面执行 `alembic upgrade/downgrade`。
- 在 Web 页面修改数据库账号、`GRANT`、主从复制通道或 MySQL 全局配置。
- 自动故障切换、自动重建从库、自动恢复备份。
- 自动删除或自动修复孤立数据。
- 完整日志落库和实时日志中心；这些属于阶段二。
- worker fencing、heartbeat 监督、最终结果原子提交等运行逻辑的正式启用；这些属于阶段三。
- 以视觉设计为目标的后台重构、复杂动效、主题系统或大屏适配。

### 2.2 不能当成已知事实的内容

数据库报告没有连接真实实例，因此下列内容在第一块完成前都必须标记为“未知”，不能用配置默认值代替：

- 实例是否已经位于 Alembic head。
- 主库与从库的实际补丁版本、字符集、排序规则、时区和事务隔离级别。
- 表的真实行数、数据量、索引量和增长速度。
- 实例实际账号权限。
- 主从复制线程、GTID、只读状态、半同步插件和真实延迟。
- `max_connections`、当前连接数、历史峰值和池耗尽情况。
- 慢查询开关和阈值是否真的在运行实例生效。
- 孤立 job、event、checkpoint、checkpoint write 和异常任务状态的数量。

### 2.3 当前必须优先处理的缺口

| 缺口 | 当前事实 | 处理位置 |
|---|---|---|
| 管理接口权限 | `app/admin/routes.py` 只校验登录，普通用户也可能读取敏感运维信息 | 第一块先限制为开发/内网与显式操作员；第二块完成管理员角色闭环 |
| 指标来源不明确 | `get_db_health()` 使用 eventual read，返回结果没有主库/从库来源 | 第一块修正 |

| checkpoint 生命周期不完整 | 会话删除不会自动删除 checkpoint；`delete_thread()` 没有调用点 | 第二块设计并实施，第三块做历史数据收口 |

| 并发安全结构不足 | job 没有 fencing token，事件和最终消息缺少稳定幂等标识 | 第二块只做兼容性预留，阶段三启用 |

## 三、第一块：只读事实与 MVP 可视化看板

### 3.1 目标

第一块只回答“数据库现在是什么状态”，不改变“数据库现在的状态”。允许修改 Python 和静态前端代码，但新增的数据库访问路径必须使用只读账号，不执行任何业务写入、结构变更、迁移或自动修复。

第一块完成后，应能通过一个受限的单页看板查看真实实例状态，并能导出或保存同口径的只读审计结果，作为第二块实施前的基线。

### 3.2 强制只读边界

- 新增检查逻辑固定使用 `MYSQL_READ_USER`；强一致事实读取主库，允许延迟的容量统计才可读取健康从库。
- 复制状态只使用 `MYSQL_REPLICA_STATUS_USER`。
- 不调用 `get_write_connection()`、`get_db_connection()` 或任何带 `commit()` 的路径。
- 允许的 SQL 类型限定为 `SELECT`、`SHOW`、`EXPLAIN` 以及读取 `information_schema`、`performance_schema`。
- 禁止 `INSERT`、`UPDATE`、`DELETE`、`REPLACE`、`ALTER`、`CREATE`、`DROP`、`TRUNCATE`、`GRANT`、`REVOKE`、`CALL` 和迁移执行。
- 不提供用户输入 SQL；前端参数只允许固定枚举、分页、排序和有上限的 `limit`。
- 默认使用轻量查询。精确 `COUNT(*)`、全表一致性扫描等高负载检查归入“深度审计”，必须由操作员显式触发，并配置超时和执行说明。

### 3.3 过渡期访问控制

当前数据库没有管理员角色闭环，因此第一块看板不能直接作为公开生产功能上线。

第一块采用以下临时门禁：

1. 增加默认关闭的数据库看板功能开关。
2. 仅允许显式配置的操作员用户访问。
3. 开发环境或可信内网才可启用。
4. 未启用、未登录或不在操作员范围内时，不返回任何数据库拓扑与指标。
5. 第二块管理员角色完成后，删除临时操作员判断，统一改为管理员权限校验。

这是一条阶段过渡措施，不替代正式管理员授权。

### 3.4 工作包

#### 1A-01：建立统一的只读检查服务

建议新增独立的只读检查模块，由 CLI 审计和管理 API 共同调用，避免 `monitoring.py` 与 `audit_before_db_upgrade.py` 各自维护不同口径。

主要工作：

- 封装主库只读、从库只读和复制状态三种数据来源。
- 每一项结果统一返回：`status`、`value`、`observed_at`、`source_role`、`source_alias`、`is_estimate`、`warning`。
- 单项查询失败只让对应卡片进入 `unknown/error`，不让整个看板返回 500。
- 对异常文本做脱敏，不返回数据库密码、连接串、Cookie、密钥或带参数的原始 SQL。
- 所有函数补充职责、数据来源和一致性级别说明。

预计涉及：

- `Database/monitoring.py`
- `Database/audit_before_db_upgrade.py`
- 可新增 `Database/inspection.py`
- `app/db.py`
- `config/settings.py`

#### 1A-02：补齐数据库事实清单

第一版看板和审计至少覆盖：

1. Alembic：仓库 head、实例 `alembic_version`、是否一致。
2. 节点：主库与第一从库的 `SELECT VERSION()`、连接成功状态和采集来源。
3. Schema：关键表是否存在，关键字段、索引、外键是否与目标结构一致。
4. 表容量：`table_rows`、`data_length`、`index_length`、总大小，并明确 InnoDB 行数为估算值。
5. 数据完整性：
   - 消息缺少会话或用户；
   - 附件缺少消息；
   - job 缺少用户或会话；
   - job event 缺少 job；
   - checkpoint write 缺少 checkpoint；
   - checkpoint 缺少对应 session；
   - 父 checkpoint 缺失；
   - archived session 缺少用户；
   - 活跃 job 与 `active_session_key` 不一致；
   - 达到最大重试次数但仍为 `running`；
   - 长时间无 heartbeat 的 `running` job。
6. 主从：IO/SQL 线程、延迟、最近错误；MVP 只展示当前配置中的第一从库。
7. 字符与时间：server/database charset、collation、MySQL 时区、system time zone、事务隔离级别。
8. 权限：只核对各应用账号是否满足职责，不在前端展示完整用户名、host 或原始 grants。
9. 连接：`max_connections`、`Threads_connected`、`Threads_running`、`Max_used_connections`。
10. 慢查询：实际开关、阈值、输出方式、累计 `Slow_queries` 和 digest 摘要；明确 digest 摘要不是慢查询日志原文。

#### 1A-03：整理只读 API

保留已有 API，避免无必要的破坏性改名；在此基础上统一响应结构并增加只读端点。

建议最小接口：

| 接口 | 用途 | 一致性 |
|---|---|---|
| `GET /api/admin/db/overview` | 看板首屏汇总与各区块状态 | 关键事实强一致，容量指标可延迟 |
| `GET /api/admin/db/schema` | revision、表、字段、索引、外键 | 主库只读 |
| `GET /api/admin/db/integrity?mode=quick` | 快速完整性审计 | 主库只读 |
| `GET /api/admin/db/slow-queries?limit=20` | 慢查询配置与 digest 摘要 | 必须标明节点来源 |
| `GET /api/admin/jobs/workers` | 当前 worker/job 快照 | 主库强一致 |

约束：

- `limit` 设置服务端上限。
- 不在 URL 或响应中出现数据库凭据。
- 返回 `observed_at`，前端不把旧数据伪装成实时状态。
- 同一接口允许部分区块失败，并返回区块级 warning。
- 已有 `/db/health` 可以保留为兼容接口或内部调用，不在本阶段强制删除。

#### 1A-04：实现单页 MVP 看板

使用当前 Flask 静态资源方案新增一个数据库管理单页，不引入前端框架和构建工具。

页面只需要：

- 顶部状态卡：revision、主库、从库、阻塞审计数、连接使用率。
- 节点区：版本、复制线程、延迟、采集时间和数据来源。
- 表容量表：表名、估算行数、数据、索引、总大小。
- 完整性区：检查名、严重级别、数量、状态和说明。
- 慢查询区：实际配置与前 N 条 digest 摘要。
- worker/job 区：queued、running、stale 和达到最大尝试次数的任务。
- 手动刷新按钮、最后更新时间、加载态、空态、失败态。

页面暂不需要：

- 拖拽布局、主题切换、复杂图表库、实时 WebSocket、逐秒自动刷新。
- 任意 SQL 输入框。
- 修改、修复、删除、迁移、主从控制按钮。
- 对移动端和所有浏览器做像素级适配。

建议新增：

- `app/static/db_admin.html`
- `app/static/js/db_admin.js`
- `app/static/css/db_admin.css`

#### 1A-05：只读验证

必须完成：

- 单元测试验证新增查询没有 DML/DDL 语句。
- 使用只授予读取权限的账号调用全部看板 API；即使没有写权限也能正常工作。
- API 权限测试覆盖：功能关闭、未登录、非操作员、允许的操作员。
- 主库正常、从库不可用、`performance_schema` 无权限、单项查询超时时，页面均能显示部分结果。
- 验证每个指标都带采集时间和来源。
- 检查 HTML、CSS、JS 引用关系，以及加载态、空态和失败态。
- 在临时或开发数据库执行 quick audit；不对生产数据执行深度扫描。

## 四、第二块：受控数据库写操作

### 4.1 进入条件

只有同时满足以下条件才进入第二块：

- 第一块真实实例报告已经生成。
- 实例当前 revision、孤立数据、外键、账号权限和主从状态已经明确。
- 已确认是否存在真实用户、不可停机要求和备份恢复能力。
- 计划执行 migration 前已完成可恢复备份或临时库恢复演练。
- 第一块发现的阻塞项已经形成逐项处理决定，不能带着未知结构直接升级。

### 4.2 写操作总原则

- 只实现白名单内的业务操作，不接受用户提交 SQL。
- 所有写入固定使用写账号并写主库。
- 每个写操作必须有管理员权限校验、参数校验、事务、影响行数检查和明确返回结果。
- 可预览的操作先返回影响范围，再由用户确认执行。
- 可逆操作优先；删除、批量修复和结构操作不放进第一版 Web UI。
- 不在请求中输出数据库异常原文、SQL 参数、凭据或用户密码。
- 阶段二日志系统完成前，管理员写操作至少写现有结构化服务日志并带 request ID；不得假装已经具备完整持久审计能力。

### 4.3 第一批允许和禁止的操作

| 类型 | 第二块是否允许 | 说明 |
|---|---|---|
| 启用/禁用普通用户 | 允许 | 可逆；禁用后下一请求和下一次登录必须立即失效 |
| 普通用户/管理员角色切换 | 允许 | 保护最后一个管理员，禁止自我误锁死 |
| 创建初始管理员 | 允许，但只通过 CLI | 不提供公开注册管理员接口，不从前端接收初始管理员密码 |
| 会话删除时同步清理 checkpoint | 允许 | 作为现有业务删除事务的完整性修复 |
| 执行预定义数据修复脚本 | 只允许人工 CLI | 必须先预览、备份并输出前后审计结果 |
| 删除用户、批量删除、批量归档 | 暂不进 Web UI | 影响范围大，放到第三块完成生命周期规则后决定 |
| Alembic upgrade/downgrade | 禁止通过 Web | 仅由部署流程执行 |
| 修改 MySQL grants/变量/复制 | 禁止 | 运维操作不进入应用后台 |
| 任意 SQL/DDL | 永久禁止 | 不属于本项目数据库管理后台职责 |

### 4.4 工作包

#### 1B-01：建立正式管理员闭环

建议以最小模型实现两种角色：

- 在 `users` 表新增 `role`，值限定为 `user/admin`，默认 `user`。
- 老用户升级后统一为普通用户。
- 初始管理员通过一次性 CLI 创建或提升，密码不经过前端和日志。
- `find_user()`、`find_user_by_id()` 和 session guard 同时读取并校验 `is_active` 与 `role`。
- 禁用用户不能登录；已有 session 在下一请求被清理。
- 管理 API 使用统一管理员装饰器，不再散落 `_require_login()`。
- 禁止禁用、降级或删除最后一个管理员。
- 管理员修改自身状态或角色时增加额外确认，避免把系统锁死。

数据库变更必须通过新的 Alembic migration，并同步更新 `check_database_readiness()` 是否需要字段级检查。

#### 1B-02：修正迁移与连接安全问题

- 修正 `Database/migrations/env.py` 的连接 URL 构造，正确处理用户名和密码中的 URL 特殊字符。
- 冻结职责：Alembic 唯一改 schema，`database_init.py` 不建业务表。
- 为 migration 建立“空库升级”和“现有 head 前一版本升级”两条验证路径。
- 每个新增 migration 提供自洽 downgrade；生产回退以备份和向前修复为主，不把 downgrade 当成唯一恢复手段。
- 不直接修改现有 migration 文件。

#### 1B-03：补齐 checkpoint 生命周期和幂等约束

按照第一块真实审计结果选择最小方案：

1. 先验证当前应用是否始终满足 `checkpoints.thread_id == sessions.id`。
2. 若该关系成立且历史数据干净，追加 checkpoint 与 session 的所有权约束或在同一事务中显式清理 checkpoint。
3. 会话删除必须同时处理 checkpoint 和 pending writes，失败时整个删除事务回滚。
4. 为 `checkpoint_writes` 增加 `(thread_id, checkpoint_ns, checkpoint_id, task_id, idx)` 唯一约束。
5. `put_writes()` 改为与唯一约束一致的幂等写入策略。
6. “最新 checkpoint”排序增加稳定的第二排序键，不能只依赖 `created_at`。
7. 历史孤立 checkpoint 不在 migration 中静默删除；先生成修复清单，再由人工脚本处理。

如果第一块发现 thread 与 session 不是一一对应，则停止直接加外键，先单独设计 thread 所有权映射，不能凭假设迁移。

#### 1B-04：为阶段三预留兼容结构

只做“扩展”，不改变现有 worker 运行语义：

- 为 `analysis_jobs` 预留单调递增的 `lease_token` 或等价 fencing 字段。
- 为任务事件预留可空 `event_uuid` 和租约来源字段，旧 worker 可继续写空值。
- 为任务生成的最终消息预留可空幂等键，旧消息不要求回填。
- 新字段先允许旧代码兼容；非空和严格状态约束等“收紧”动作留到阶段三启用新协议后执行。
- 字段和唯一键只有在阶段三协议已明确到足以命名、约束和回滚时才创建，避免提前固化错误状态机。

#### 1B-05：实现受控管理 API 与 MVP 操作区

第一批 API 只覆盖：

- 用户列表和详情只读查询。
- 启用/禁用普通用户。
- 普通用户与管理员角色切换。
- 当前管理员身份和权限确认。
- 操作结果返回 request ID、目标、变更前状态、变更后状态和影响行数。

前端仅增加：

- 用户状态与角色表格。
- 单条启用/禁用、角色切换按钮。
- 二次确认对话框和清晰错误提示。
- 没有批量操作，没有自由 SQL，没有迁移按钮。

#### 1B-06：写操作验证

必须覆盖真实 MySQL 的集成测试：

- 普通用户调用写接口返回 403。
- 禁用用户不能登录，已有 session 下一请求失效。
- 最后一个管理员不能被禁用或降级。
- 两个管理员并发修改最后管理员时，数据库事务仍保证至少保留一个管理员。
- checkpoint pending writes 重复写入不产生重复行。
- 删除会话后不残留对应 checkpoint 和 pending writes。
- migration 可从空库升级到 head。
- migration 可从现有结构快照升级。
- 临时数据库 downgrade 自洽，或清楚记录不能在线回滚的原因和备份恢复步骤。
- 预留字段存在但不改变旧 worker 的领取、心跳和完成行为。

### 4.5 第二块交付物

- 正式管理员角色与用户启用状态闭环。
- 一组追加式 Alembic migrations。
- 安全的 Alembic URL 构造。
- checkpoint 生命周期和 pending writes 幂等约束。
- 阶段三所需的兼容性预留字段。
- 仅包含白名单操作的管理 API 与 MVP 操作区。
- 数据库写入、并发保护、迁移升级与回滚相关测试。

### 4.6 第二块验收门槛

- [ ] 所有 schema 变化都来自新增 Alembic migration。
- [ ] 普通用户无法读取或调用管理 API。
- [ ] 用户禁用和管理员角色修改形成业务闭环。
- [ ] 系统始终至少保留一个可用管理员。
- [ ] 所有写操作走主库并处于明确事务中。
- [ ] Web UI 不存在任意 SQL、迁移、账号授权和复制控制能力。
- [ ] 会话删除不再产生孤立 checkpoint。
- [ ] pending writes 重试不会重复。
- [ ] 旧 worker 在兼容迁移后仍可运行。
- [ ] 备份、升级、验证和恢复步骤已经演练并记录。

## 五、第三块：治理完善与阶段收口

### 5.1 目标

第三块不再扩张功能面，而是把前两块从“能用”收口到“可以稳定进入阶段二”。重点是数据生命周期、主从口径、连接容量、事务规则、测试和发布门禁，不以重做前端为完成标准。

### 5.2 工作包

#### 1C-01：完成数据生命周期

- 明确用户、会话、消息、附件、文件、job、event、checkpoint、checkpoint writes 和 archived session 的删除/保留关系。
- 为用户删除和会话删除提供影响预览；未完成持久审计前，用户物理删除不默认开放到 Web UI。
- 历史孤立数据只通过专用 CLI 修复，执行前输出数量与主键范围，执行后重新审计。
- 修复脚本默认 dry-run，实际执行需要显式参数、备份确认和事务批次上限。
- 不在审计脚本中混入自动修复。
- 确定 checkpoint 和 job/event 的保留周期，但实际定时清理可在日志与任务安全阶段统一实现。

#### 1C-02：冻结逐接口读写一致性矩阵

至少形成以下结论并落实到代码：

- 登录、角色、用户状态、任务状态、实时 SSE、当前 checkpoint：主库强一致读。
- job 创建、领取、心跳、事件、终态、用户管理：主库写。
- 历史会话列表、文件列表、历史日志、非实时统计：副本健康时可延迟读。
- Schema revision、外键、权限和结构审计：主库只读。
- 数据库监控必须返回节点来源，不能把从库指标当作主库指标。

对所有业务 SQL 做一次调用点清单，修正明显误用；不做全局 Repository 重构。

#### 1C-03：收口高风险事务

优先统一：

- 用户启用、禁用和角色变化。
- 会话删除及 checkpoint 清理。
- 创建 job。
- 保存聊天和附件。
- checkpoint 与 pending writes。
- 为阶段三准备的任务终态写入接口。

每个事务明确：前置状态、锁范围、成功提交、异常回滚、影响行数和允许重试的错误。`execute_with_timing()`、`db_cursor()` 等现有封装要么被关键路径实际采用，要么明确缩小职责，避免“看似统一、实际绕过”。

#### 1C-04：连接池和主从完善

- 按 Web 进程、worker 进程、worker slot、迁移、监控和未来管理请求计算理论最大连接数。
- 读取真实 `max_connections` 与 `Max_used_connections`，设定安全余量和告警阈值。
- 明确连接获取超时、锁等待超时、事务超时和死锁重试边界。
- 从库状态查询增加短时间缓存，避免每次 eventual read 都创建状态连接；缓存失效时安全回退主库。
- 第一块只展示第一从库，第三块再支持 `MYSQL_READ_HOSTS` 中每个从库逐节点展示。
- 不在本阶段实现自动故障切换。

#### 1C-05：MVP 前端完善

只做影响可用性的完善：

- 表格分页、固定上限和基础筛选。
- 区分 `healthy/warning/error/unknown`，不把“取不到”显示为“正常”。
- 所有写按钮显示影响对象、前后状态和操作结果。
- 防重复提交，提交期间禁用按钮。
- 页面刷新后重新拉取服务端事实，不依赖前端缓存判断成功。
- 基础响应式布局、键盘可操作和可读颜色对比。

不做主题系统、复杂图表、动画大屏、拖拽布局和完整设计语言。

#### 1C-06：发布门禁与文档收口

- 空库执行 `alembic upgrade head`。
- 现有结构快照升级到 head。
- 升级前 quick/deep audit、升级后复查。
- 临时数据库验证 downgrade 或备份恢复。
- 主从环境验证强一致路径不读副本、eventual 路径可安全回退。
- 关闭/开启看板功能开关各验证一次。
- 完整 API 权限回归和前端最小交互验证。
- 更新 README、AGENTS.md、迁移说明、运维手册和开发日志；只更新发生真实变化的项目事实。

### 5.3 第三块交付物

- 数据生命周期矩阵和可审计的 dry-run 修复工具。
- 逐接口强一致/可延迟读/写主库矩阵。
- 高风险事务说明与对应测试。
- 多节点监控、连接容量基线和超时策略。
- 可稳定使用但保持简洁的 MVP 管理页面。
- 完整的升级、验证、恢复和发布清单。

### 5.4 阶段一总验收门槛

满足以下全部条件，才能进入阶段二日志管理：

- [ ] 真实数据库 revision 已确认且目标实例位于计划要求的 head。
- [ ] 数据库事实看板的每项数据都标明节点来源、时间和估算属性。
- [ ] 只读审计覆盖核心表、job、event、checkpoint 和任务状态一致性。
- [ ] 普通用户完全无法访问数据库管理页面和 API。
- [ ] 管理员、用户启用状态和最后管理员保护已闭环。
- [ ] Alembic 是唯一 schema 入口，空库与现有结构升级均通过。
- [ ] 会话删除不会留下 checkpoint 或 pending writes。
- [ ] 新的幂等和租约预留结构与旧 worker 兼容。
- [ ] 强一致、可延迟读和写主库矩阵已经落实。
- [ ] 连接池容量有真实数据依据，不使用拍脑袋默认值。
- [ ] 不存在任意 SQL、Web migration、账号授权或复制控制功能。
- [ ] 前端具备基本可视化、加载态、空态、失败态和受控写入反馈。
- [ ] 备份、升级、复查和恢复流程已经在非生产环境演练。

## 六、推荐实施批次

为降低评审和回退成本，建议按以下批次提交，但不在本计划阶段主动执行 `git commit`：

| 批次 | 内容 | 数据库变更 |
|---|---|---|
| A1 | 只读检查服务、扩展审计、单元测试 | 无 |
| A2 | 只读 API、临时访问门禁、API 测试 | 无 |
| A3 | Flask 静态 MVP 看板、文档 | 无 |
| B1 | 管理员字段 migration、认证与管理员授权闭环 | 有，追加式 |
| B2 | checkpoint 生命周期、pending writes 幂等 migration 与代码 | 有，追加式 |
| B3 | 受控用户状态/角色写 API 与 MVP 操作区 | 仅业务写入 |
| B4 | 阶段三兼容字段 migration | 有，扩展式 |
| C1 | 读写矩阵、高风险事务和数据生命周期收口 | 视审计结果决定 |
| C2 | 多从库、连接容量、超时和缓存 | 通常无 schema 变化 |
| C3 | 集成测试、升级恢复演练、文档和前端可用性完善 | 无新增功能性 schema |

推荐分支名：

```text
docs(database)/phase-one-detailed-plan
```

后续实现分支应按实际批次拆分，例如：

```text
feat(database)/readonly-dashboard
feat(database)/admin-write-controls
fix(database)/checkpoint-lifecycle
```

## 七、风险与停止条件

遇到以下任一情况，停止进入下一块，先形成专项处理方案：

- 实例 revision 无法确定或 migration 链与实际表结构不一致。
- 第一块发现孤立数据，但没有备份或无法判断业务归属。
- 主库与从库版本、GTID 或复制状态异常。
- 应用读账号拥有 DDL/DML 权限，或写账号权限远超职责。
- `checkpoints.thread_id` 并不稳定对应 `sessions.id`。
- 生产环境存在不可停机要求，但 migration 未完成锁影响评估。
- 无法保护最后一个管理员，或无法让禁用用户的已有 session 失效。
- 兼容字段会导致旧 worker 读取、写入或索引计划发生不可接受变化。
- 深度审计查询可能造成明显锁等待或高负载，但还没有超时和执行窗口。

## 八、计划完成后的直接下一步

阶段一完成后再进入阶段二日志管理。阶段二可以依赖本阶段提供的管理员权限、数据库事实来源、主从读取矩阵和安全写入边界，建立 WARNING/ERROR 落库、脱敏、关联上下文、历史查询与管理员 SSE。阶段三再启用本阶段预留的 fencing、幂等和严格状态转换协议。
