# 多模态知识摄取、文本化检索：完整开发规划

状态：最终版规划（v1.0，2026-07-16）  
范围：知识库维护者离线摄取知识源；用户查询仍为文字，用户 CSV 因果分析流程保持不变。  
关键假设：新增 PDF、图片、文字和表格知识源由开发者提交，用于扩充现有共享的默认因果知识库；资料不包含医疗隐私等敏感数据，当前没有普通用户提交共享知识源的计划。如果未来需要独立业务语料或用户私有知识库，应新增 `custom` 语料配置并重新设计 collection 隔离，而不是使用 `multimodal` 这个名称。  
配套文档：[技术调研](./多模态知识摄取技术调研.md)、根目录 `CONTEXT.md`、`docs/adr/0001-textualize-multimodal-knowledge-before-retrieval.md`。

## 1. 目标与边界

### 目标

1. 支持从 TXT、Markdown、CSV、XLSX、PDF、PNG、JPEG、WebP、TIFF 摄取知识。
2. 对数字 PDF 提取正文与版面；对扫描页和图片执行 OCR；对图表、流程图和因果图优先生成结构化文字，无法可靠识别时标记人工复核，不用笼统描述掩盖结构缺失。
3. 将所有模态统一为带来源定位的文字知识片段，再生成现有文字嵌入模型可处理的知识块。
4. 保留文件、页码、工作表、行范围、页面区域、提取方式和版本，使回答证据可追溯。
5. 支持重复运行、失败隔离、暂存索引验证和显式发布，不污染当前生产知识库。
6. 建立按模态分层的提取、检索和回答回归测试。

### 非目标

- 不支持图片作为用户查询。
- 不做以图搜图或原生图文联合向量检索。
- 不把 `/api/upload_file` 扩展成知识库上传接口；它继续只处理用户 CSV 分析文件。
- 首版不提供任何知识摄取管理 UI；开发者也只使用 CLI。
- 首版不支持 DOCX、PPTX、音频和视频；统一接口稳定后再添加适配器。
- 不在开发或测试中清空、覆盖 `Agent/knowledge_base/db/`。

### 默认决策

- 首版采用“本地 OCR + 可选视觉模型描述”。视觉模型不可用时，OCR 可继续工作，并在摄取报告中记录降级警告。
- 首版采用“多模态知识摄取、结构化文本化、统一文字 embedding”，不引入原生图片向量、以图搜图或图文联合向量空间。
- 查询、稀疏检索、重排、回答生成和 RAG 评测继续消费文字内容。
- 首版唯一维护入口为 CLI，不开发管理页面，不引入数据库 schema 变更；第二版再与现有 RAG 评测工作台接轨。
- CPU 是本地解析、OCR 和文字 embedding 必须可运行的兼容基线，GPU 仅作为可选加速；本地视觉模型如确实需要 GPU，CPU 开发者可选择关闭视觉或显式使用远程视觉。所有路径必须输出相同的公开契约和质量报告。
- 远程视觉模型默认关闭；即使当前资料不敏感，也必须由开发者显式允许数据外发，并受最大调用图片数限制；只有 adapter 具备币种和可验证计价规则时才启用金额门禁。
- 新资料默认以共享因果知识库为目标，但必须先写入暂存索引，通过质量门禁后由开发者显式发布，不能直接追加到活动 collection。
- 首版发布单位是 profile 权威 source root 的完整语料快照，不实现增量 append；临时 `--source` 覆盖可用于 inspect、测试和暂存摄取，但默认不可发布，避免把单文件试跑误切成完整活动知识库。
- profile 只表达语料/知识域，不表达文件模态：`default` 扩展为多格式因果知识源摄取；`medical` 继续读取 PubMedQA processed JSONL。本阶段不新增 `multimodal` profile。
- `--source` 仅用于覆盖 `default` 的知识源目录或指定单次摄取来源，不改变目标 profile 的语料归属、embedding 和 collection 配置，也不自动获得发布资格。

### 已确认的产品条件

| 条件 | 已确认范围 | 对实现的约束 |
|---|---|---|
| 提交者 | 仅开发者/知识库维护者 | 首版只做 CLI，不接普通用户文件路由 |
| 数据敏感性 | 当前资料不敏感，不包含医疗隐私 | 可选远程视觉能力仍需显式启用和审计，不能静默外发 |
| 部署设备 | 不同开发者可能只有 CPU，也可能有 GPU | `cpu/gpu/auto` 共享同一流水线；CPU 必须覆盖所有格式的本地解析、OCR 和文字 embedding，GPU 只加速或承载可选本地视觉模型 |
| 目标知识库 | 共享默认因果知识库 | 先 staging、后 evaluate、再 publish，不直接污染活动索引 |
| 用户查询 | 继续使用文字问题 | 首版保持文字 embedding、Chroma、rerank 和证据链路 |
| 页面范围 | 首版无摄取管理页面 | 第二版接入现有 `/rag_eval` 工作台，复用首版字段和深模块 interface |

### 首版支持格式

首版使用明确白名单，不以“常见格式”作为验收口径：

- 文字：`.txt`、`.md`
- 表格：`.csv`、`.xlsx`
- 文档：`.pdf`
- 图片：`.png`、`.jpg`、`.jpeg`、`.webp`、`.tif`、`.tiff`

首版不支持 DOC/DOCX、PPT/PPTX、旧版 XLS、SVG、音频、视频、压缩包和加密 PDF；后续只能基于真实资料需求新增适配器。

## 2. 当前仓库事实

- `build_knowledge.py` 的 `default` profile 只加载 TXT 和 PDF；PDF 当前只走 PyMuPDF/PyPDF 文字提取。
- `medical` profile 从 PubMedQA JSONL 生成纯文字 `Document`。
- PubMedQA 原始资料来自外部数据集，但当前构建读取仓库内已经处理好的本地 JSONL，不会在每次构建时联网下载。
- 构建链路为“加载 → `RecursiveCharacterTextSplitter` → 文字 embedding → Chroma”。
- `query_rag.py` 读取 `page_content`，并对同一文字 embedding 执行 dense、MMR、sparse 和 rerank。
- 当前 `build_knowledge.py` 的 default 与 medical 本地 embedding 都硬编码 `device=cpu`，尚无统一的 `auto/cpu/gpu` 设备解析。
- 当前 `doc_id` 主要来自文件标题 slug，存在同名文件冲突风险。
- 当前非空 collection 默认拒绝追加；`--allow-append` 不能承担可靠增量更新或发布职责。
- `build_knowledge.py` 的 default collection 默认值是 `causal_agent_default`，`query_rag.py` 的查询默认值却是 `pubmedqa_clean`；在统一运行时索引解析前，不能假定 default 构建结果会被正式查询使用。
- 当前本地 Chroma 同时存在 `causal_agent_default` 和 `pubmedqa_clean`；collection 名称不能证明真实语料归属，legacy fallback 必须用内容/benchmark 指纹校验，不能把 `causal_agent_default` 按名称直接登记为因果 default。
- worker 启动检查硬编码 `Agent/knowledge_base/db`，而查询侧支持 `RAG_VECTOR_DB_DIR`，两处配置尚未统一。
- 当前证据只稳定输出文件、标题、页码等字段，尚无工作表、行范围、页面区域和提取方式。
- `/api/upload_file` 只接受 CSV，并把内容存入 MySQL `uploaded_files`，该路径与共享知识库无关。
- `requirements.txt` 已包含 PyMuPDF、Unstructured、pandas；尚未形成 OCR、XLSX 和视觉解析的完整生产依赖。
- 新增的 `tests/test_*.py` 会被根 `.gitignore` 的 `tests/` 规则忽略；P00 将精确放行专用 `tests/rag_ingestion/` 子树，不全局取消 `tests/` 忽略。
- 根 `.gitignore` 整体忽略 `docs/`，因此当前 ADR 只在本工作区可见；P00 将精确放行 `docs/adr/0001-textualize-multimodal-knowledge-before-retrieval.md`，不全局取消 `docs/` 忽略。
- 当前 `/rag_eval` 页面和 `/api/rag_eval/*` 接口没有维护者权限保护；第二版增加摄取和索引发布能力前必须补专用授权检查。
- 当前 RAG 评测的实时进度、取消标记和 SSE 回放保存在 Flask 进程内存，历史报告保存在 `RUNS_DIR` 文件目录；第二版只能复用页面交互和报告约定，不能直接把长时间摄取任务继续放进 Web 进程线程。
- 当前开发/主从 compose 会把 `Agent/knowledge_base/db` 挂载到 app 和 worker 的相同容器路径；`docker-compose.prod.yml` 仍挂载旧的 `./knowledge_base/db:/app/knowledge_base/db`，且没有 worker 服务，不能满足活动索引注册表和长任务在生产拓扑共享的要求。

### Profile 与文件适配器的职责

| 层级 | 回答的问题 | 当前/目标值 |
|---|---|---|
| Profile | 这批知识属于哪套语料，使用哪组 embedding、collection 和分块策略？ | `default`、`medical` |
| Source | 这次从哪个目录或文件摄取？ | 默认 source 目录或 `--source` 覆盖 |
| Adapter | 这个知识源如何转换为统一知识片段？ | text、table、pdf、ocr、vision |

目标关系：

- `default`：保持现有默认因果知识库语义，在原 TXT/PDF 基础上增加 Markdown、CSV、XLSX 和图片适配器；PDF adapter 同时增强数字、扫描和混合页面处理。
- `medical`：保持现有 PubMedQA processed JSONL 路径和 benchmark 匹配保护，本轮不改成文件目录摄取。
- 所有 adapter 输出相同的 `KnowledgeFragment`，因此将来如果 medical 需要加载医学 PDF/图片，可以复用 adapter，而不需要再创建 `medical_multimodal` profile。

## 3. 目标模块设计

CLI 与第二版 HTTP adapter 只面对一个深模块 interface；格式识别、解析、OCR、视觉描述、规范化、分块、缓存、评测和索引生命周期全部隐藏在模块内部。调用方只提交领域命令并读取领域结果，不接触 Docling、PaddleOCR、Chroma collection 或本机模型对象。

```text
CLI adapter --------+
                    +--> KnowledgeBaseMaintenance.execute(MaintenanceCommand)
HTTP adapter -------+                         |
                                              +-- inspect：来源发现、安全校验、预计解析路径
                                              +-- ingest：解析、规范化、分块、暂存索引
                                              +-- evaluate：提取质量与检索质量门禁
                                              +-- publish/rollback/status：索引生命周期
                                                                    |
                                                                    v
                                                          MaintenanceResult
```

外部 seam 只暴露一个 interface：

```python
result = knowledge_base_maintenance.execute(command)
```

`MaintenanceCommand` 是 `inspect/ingest/evaluate/publish/status/rollback` 的带类型联合；`MaintenanceResult` 返回运行状态、`run_id`、可选 `index_version`、报告引用和结构化问题。CLI 参数和第二版 HTTP 请求只负责转换成该命令，不能绕过 interface 直接操作内部模块。

调用方需要知道的 interface 约束：

- `inspect/ingest` 请求指定知识源、profile 和运行配置；暂存 collection 名称由实现生成，不属于调用方 interface。
- 返回完整报告，不以控制台输出作为机器契约。
- 单个知识源失败不应破坏其他知识源的结果；最终状态区分 `passed`、`partial`、`failed`、`cancelled`。
- `partial` 可以保留诊断产物和暂存索引，但默认 `publishable=false`；只有所有权威知识源处理成功且不存在阻塞性问题时才能通过 evaluate。
- 所有产物 ID 在相同源内容、提取器版本和分块配置下必须稳定。
- `ingest` 只生成不可变的暂存 `index_version`，不直接切换活动索引。
- `publish` 只接受已经通过质量检查的 `index_version`，并返回可审计的发布报告。
- `rollback` 只能切换到仍存在、指纹可验证且曾通过门禁的历史 `index_version`。

摄取运行状态至少遵循：

```text
created -> inspected -> ingesting -> staged -> evaluated_pass -> published
                                  \-> evaluated_fail
任意执行阶段 -> partial / failed / cancelled
```

内部只有确实存在替代实现的位置设置 seam：

- OCR：生产本地适配器 + 测试 fake。
- 视觉描述：OpenAI-compatible/其他生产适配器 + 测试 fake；未来可加本地 VLM。
- 索引写入：Chroma 适配器 + 内存测试适配器。
- 活动索引注册表：本地原子文件适配器 + 内存测试适配器。
- TXT、CSV、XLSX、PDF 的本地解析不为每个库额外暴露公共 port。

## 4. 统一产物契约

### KnowledgeFragment

必须至少表达：

| 字段 | 约束 |
|---|---|
| `source_id` | 逻辑来源 ID；由 profile + source root 下规范化相对路径或 manifest 显式 ID 生成，不依赖本机绝对路径，文件更新后保持不变。相对路径统一 `/` 分隔和 Unicode NFC、保留大小写，并拒绝 casefold 后冲突的两个来源 |
| `content_sha256` | 原始文件内容 SHA-256；用于识别版本变化、缓存命中和完整性校验 |
| `source_version_id` | `source_id + content_sha256` 的稳定指纹，区分同一逻辑来源的不同版本 |
| `fragment_id` | `source_version_id + locator + content_kind + extractor fingerprint + normalized text hash` 的稳定哈希；CPU/GPU 输出若有内容差异不得产生同 ID 异文 |
| `source_name` | 原始文件名 |
| `source_type` | `text/table/pdf/image` |
| `content_kind` | `text/table/ocr/formula/chart/causal_graph/image_description` |
| `text` | 非空的文字化内容 |
| `locator` | 页码、工作表/行范围、bbox 中适用的部分 |
| `title/section` | 可为空，但字段存在 |
| `extractor/extractor_version` | 可重现性与缓存失效依据 |
| `confidence` | 可为空；OCR/视觉结果建议提供 |
| `warnings` | 结构化警告，不混入正文 |

`locator` 在 P01 固定为跨解析器契约：页码、文字行号和表格行号均从 1 开始，范围为闭区间；bbox 使用左上角为原点、取值 `[0,1]` 的 `x0/y0/x1/y1`，并额外保存原页面宽高供回映。解析器原生坐标只能留在内部实现或诊断报告中，不能泄漏为第二套公开字段。

### KnowledgeChunk

除检索文字外，必须继承 `source_id`、`source_version_id`、`fragment_id`、来源定位、`content_kind`、提取器版本，并基于 fragment、内容和分块配置指纹生成稳定 `chunk_id`。同一 `source_id` 发布新版本时，manifest 必须能识别并淘汰旧 `source_version_id` 的活动 chunk；原始历史索引版本保持不可变，用于审计和回滚。

Chroma metadata 采用扁平标量字段；复杂 locator 同时保存为 JSON 字符串，不假定向量库支持任意嵌套对象。字段命名和页码基准在 P01 冻结后，解析窗口不得自行新增同义字段。

### 各格式规范化规则

| 知识源 | 文字化规则 | 来源定位 |
|---|---|---|
| TXT/Markdown | 保留标题和段落层次，去除无意义空白 | 行范围或 section |
| CSV | 表头与连续行组转为 Markdown/紧凑结构化文字 | 行范围 |
| XLSX | 每个 sheet 独立；保留表头、单元格显示值和必要公式文本 | sheet + 行范围 |
| 数字 PDF | 正文按阅读顺序；表格与图片独立成片段 | page + bbox |
| 扫描 PDF | 页面渲染后 OCR；必要时附加视觉描述 | page + bbox |
| 图片/页面图形 | OCR、公式、统计图、因果图和通用视觉描述分别形成片段；因果图优先输出节点、带方向边和条件关系，不能只生成笼统 caption | bbox 或整图 |

#### 首版 CLI 命令与字段契约

首版先冻结字段含义，再实现具体参数解析。CLI 是首版唯一维护入口，也是第二版页面/HTTP interface 的字段来源，不允许页面阶段重新发明同义字段。建议入口为 `python -m Agent.knowledge_base.ingestion <command>`；旧 `build_knowledge.py` 保留兼容入口，不同时承载新旧两套参数语义。

建议命令：

```text
inspect   发现文件、校验格式与限制，输出预计解析路径和远程调用量，不写索引
ingest    解析、规范化、分块并写入暂存索引
evaluate  对指定 index version 运行摄取质量与检索门禁
publish   发布已经通过门禁的暂存索引
status    查看摄取运行或 index version 的状态、配置快照、报告和失败项
rollback  切换到指定的、已发布且可验证的历史索引版本
```

建议核心字段：

| CLI 字段 | 适用命令 | 类型/候选值 | 含义与约束 |
|---|---|---|---|
| `--source` | `inspect/ingest` | path，可重复 | 文件或目录；只改变本次来源，不改变 profile 语义。偏离 profile 权威 source root 的运行默认标记为不可发布 |
| `--profile` | `inspect/ingest` | 首版仅 `default` | 首版新 CLI 只扩展默认因果知识库；medical 继续使用旧 JSONL 构建入口 |
| `--device` | `inspect/ingest` | `auto/cpu/gpu` | 默认 `auto`；auto 可回退 CPU，显式 gpu 不可用时失败；报告记录每阶段实际设备 |
| `--ocr` | `inspect/ingest` | `auto/disabled/force` | `auto` 仅对缺少可靠原生文字的页或图片执行 OCR |
| `--ocr-languages` | `inspect/ingest` | comma-separated list | OCR 语言列表，默认值在配置中冻结并写入 config snapshot |
| `--vision` | `inspect/ingest` | `disabled/local/remote` | 默认 `disabled`；视觉描述只补充 OCR/结构解析不能表达的图表语义。显式视觉路径失败时保留 OCR/结构结果并产生 warning，是否可发布由 evaluate 决定 |
| `--allow-remote-data` | `ingest` | flag | `vision=remote` 时必填，防止静默外发；inspect 不发送资料到远程服务 |
| `--vision-max-images` | `inspect/ingest` | non-negative int | 单次摄取运行最大远程图片调用数，是首版跨供应商可执行的成本硬门禁 |
| `--run-name` | `inspect/ingest` | string，可空 | 仅用于人类识别；`run_id` 由实现生成，不接受调用方指定 |
| `--run-id` | `status` | string | 查询摄取运行，不等同于索引版本或 collection 名 |
| `--index-version` | `evaluate/publish/status` | string | 指向不可变暂存索引版本，不接受 collection 名替代 |
| `--to-index-version` | `rollback` | string | 回退目标，必须曾通过门禁且指纹仍可验证 |
| `--report-dir` | 全部 | path，可空 | 机器可读报告输出目录；默认 `Agent/knowledge_base/rag/output/ingestion/runs/<run_id>/`，不得位于活动向量库或原始知识源目录内 |
| `--output` | 全部 | `json/text` | 控制终端输出；JSON 输出作为自动化契约，不能依赖日志文本解析 |

`status` 必须且只能提供 `--run-id` 或 `--index-version` 之一；`publish/evaluate` 必须提供 `--index-version`；`rollback` 必须提供 `--to-index-version`。CLI 与第二版 HTTP adapter 复用同一 command schema validator，adapter 只处理语法和传输格式。

`inspect` 生成 `inspection_report.json`；`ingest` 生成 `manifest.json`、`ingestion_report.json`、`issues.jsonl` 和 `ingestion_summary.md`；`evaluate` 生成 `quality_report.json`、检索明细和坏例 trace；`publish/rollback` 分别生成独立的生命周期报告。配置快照必须记录设备、解析器/模型版本、OCR/视觉策略、远程调用次数与可得的费用估算、输入内容哈希、分块配置和 embedding 指纹。首版不提供含义不明确的货币预算字段；只有具体视觉 adapter 能提供币种和可验证计价规则后，才新增金额门禁。

CLI 退出码固定为：`0` 成功、`2` 参数或配置无效、`3` 摄取为 partial/failed、`4` 质量门禁或发布冲突、`130` 用户取消。`--output json` 在成功和失败时都输出同一 `MaintenanceResult` schema，错误详情写入 `issues`，不能要求调用方解析 traceback 或中文日志。

## 7. 第二版：接入现有 RAG 评测工作台

第二版在首版 CLI、深模块 interface、报告与字段契约稳定后，接入当前 `/rag_eval`（兼容 `/rag-eval`）工作台。页面只是 `KnowledgeBaseMaintenance` 的 HTTP adapter，不直接调用 Docling/PaddleOCR/Chroma，也不复制一套 UI 专用摄取逻辑。

### 接轨原则

1. CLI 和页面共同穿过 `KnowledgeBaseMaintenance.execute()` interface，不能通过启动 CLI 子进程实现页面功能。
2. 首版 CLI 字段是字段语义的单一来源；第二版 HTTP 请求使用相同名称、枚举、默认值和校验规则。
3. 页面运行必须保存 config snapshot，并沿用现有 RAG 评测 run 的状态、进度、取消、历史、报告和差异比较交互语义；不得复用当前仅在 Flask 进程内存中的队列和取消标记作为持久执行基础。
4. 摄取评测与检索/Ragas 评测分阶段执行：先验证解析和 locator，再允许对暂存索引运行 retrieval/Ragas，最后才允许发布。
5. “发布摄取索引”和现有“发布正式 RAG 检索配置”是两个独立动作，页面必须明确区分，避免把索引版本和检索参数混为一谈。
6. 第二版仍只面向开发者/维护者，不把现有用户 CSV 上传接口改造成知识库管理入口。
7. `/rag_eval` 页面和 `/api/rag_eval/*` 全部接口必须增加登录校验；摄取、评测、发布、回滚和删除等操作再增加维护者授权。第二版先使用配置化维护者 allowlist，未来出现正式角色模型后再迁移，不能只依赖“页面入口不展示”。
8. 摄取和评测长任务必须由独立后台 worker 执行，Web 进程只负责校验、入队、状态查询和 SSE。现有 `analysis_jobs` 绑定用户会话语义，第二版不复用其业务表；新增独立的摄取运行/事件持久化模型，但可复用领取、心跳、取消和事件续传的实现模式。
9. 页面选择的 benchmark 必须与 `index_version.profile` 匹配；default 因果索引不能运行 PubMedQA，medical 索引不能运行因果多模态 benchmark。

### 首版 CLI 到第二版页面/HTTP interface 映射

| 首版字段/命令 | 第二版页面位置 | 第二版后端职责 |
|---|---|---|
| `inspect`、`--source`、`--profile` | 配置页的“知识源检查”区域 | 创建 inspection run，返回格式、限制、预计路径与远程调用量 |
| `--device` | 摄取运行配置 | 使用统一 validator；页面展示各阶段实际设备和 auto 回退 warning |
| `--ocr`、`--ocr-languages` | 摄取运行配置 | 保存到 config snapshot，报告按提取路径分组 |
| `--vision`、远程授权与调用上限 | 摄取运行配置的高级区域 | 远程模式二次确认，后端强制调用上限和授权校验 |
| `ingest` | 运行页的新“摄取”阶段 | 复用现有交互语义，由后台 worker 产出不可变 `index_version` |
| `evaluate` | 运行页的摄取质量/检索门禁阶段 | 展示按模态指标、坏例 trace 和是否可发布 |
| `status`、报告产物 | 历史、报告和对比页 | 保存 ingestion run/index version 关联，支持配置与指标差异比较 |
| `publish`、`rollback` | 正式配置区域的独立“索引版本”卡片 | 校验 index version 状态并审计注册表切换；不改检索参数发布文件 |

### 第二版任务边界

- 增加摄取运行 HTTP interface、持久进度事件和报告读取接口；复用现有 RAG 评测页面的 SSE 交互方式，不复用其进程内运行状态实现。
- 在 `rag_eval.html` 增加知识摄取配置、运行和索引版本展示，不在首版提前增加空页面。
- 页面字段从 interface schema/配置元数据渲染或校验，避免 JavaScript 手写默认值漂移。
- 第二版通过 Alembic 独立迁移增加摄取运行和事件表，并增加专用 worker；实施数据库结构变更前按仓库高风险操作规则单独确认。首版不为未来页面预建 schema，也不能把长任务退回 Flask 后台线程。

## 8. 跨窗口协作规则

1. 每个窗口只领取一个任务 ID，并从已合并的依赖任务开始。
2. 推荐每个任务使用独立 worktree 和符合仓库规范的分支，例如 `feat(rag)/ingestion-contract`。
3. P01 合并后，其他窗口只消费统一模型，不复制或私改字段；需要改契约时先回到 P01 形成小型契约变更。
4. P02/P03/P04/P08 可与 P01S 并行；P05/P06 必须等待 P01S，P07 必须等待 P05/P06。各任务只新增任务卡归属的模块、测试和 fixture，不碰 `build_knowledge.py`、`query_rag.py`、requirements、README、AGENTS。
5. P11、P12、P14 涉及共享文件，必须按顺序进行，避免同时开发。
6. 每个任务交付时都附：改动摘要、验证命令、未验证风险、建议提交信息；不要主动提交。
7. 任何 smoke 都设置临时 `RAG_VECTOR_DB_DIR` 和独立 `RAG_COLLECTION_NAME`。
8. 不提交模型权重、真实知识源、生成向量库、密钥或包含敏感内容的 OCR/视觉缓存。

## 9. 首版最终发布门禁

以下条件全部满足后，才算“完整开发”完成：

- 支持矩阵中的有效 fixture 均能生成知识片段和知识块。
- 数字/扫描/混合 PDF 路径均有自动化覆盖。
- 图片 OCR 与视觉描述可独立降级，外部服务故障不污染索引。
- 表格保留表头、sheet 和行范围，检索证据可返回这些定位。
- 因果图至少保留节点、带方向边、条件关系和原图 locator；无法可靠识别时进入人工复核，不生成可发布的猜测片段。
- 摄取可重复、可审计，活动索引不会被半成品覆盖。
- 只有 profile 权威 source root 的完整快照可发布；临时 `--source` 试跑不能误替换完整知识库。
- 活动索引注册表按 profile 隔离并原子切换，default 发布/回滚不改变 medical/PubMedQA 版本。
- worker 启动检查与正式查询解析同一索引配置。
- 当前 PubMedQA 检索保护与评测仍通过。
- 本地和 Docker smoke 均有记录。
- README、AGENTS 和 RAG 开发日志与实现一致。

以下内容不属于首版发布门禁：RAG 评测页面摄取表单、摄取运行 HTTP interface、索引版本页面卡片。它们属于第二版，不应阻塞 CLI 首版交付。

## 10. 主要风险与控制

| 风险 | 控制 |
|---|---|
| 把用户分析文件误接成共享知识摄取 | 独立领域术语、路由和 CLI；不复用 `/api/upload_file` |
| OCR/视觉幻觉进入知识库 | 分离 `ocr` 与 `image_description`、记录置信度/提取器、建立人工可审计 trace |
| 同名文件或重复摄取污染索引 | 逻辑 `source_id`、内容哈希、manifest、幂等写入、暂存发布 |
| 远程视觉服务泄露资料 | 显式启用、单独配置、默认本地/关闭、日志脱敏 |
| PDF 解析库“一把梭”但版面质量不可控 | 用 golden fixture 做技术 spike，以可观测结果选型 |
| 新依赖导致 Windows/Docker 安装困难 | P14 双环境 smoke，OCR 系统依赖写入 Dockerfile |
| Chroma metadata 丢失复杂定位 | 扁平标量 + locator JSON，P13 做 round-trip 测试 |
| 查询侧仍使用旧缓存/旧 collection | 统一 runtime resolver，并明确发布后 worker 重启约束 |
| 资料更新后旧 chunk 残留 | `source_id` 与内容哈希分离、完整快照构建、不可变 index version |
| 临时单文件试跑误发布为完整知识库 | 只有 profile 权威 source root 的完整快照具备发布资格 |
| CLI 与第二版页面字段漂移 | 首版冻结字段语义，第二版复用同一深模块 interface、枚举、默认值和 validator |
| 索引发布与检索配置发布混淆 | 页面与 HTTP interface 使用不同资源和动作名称，分别记录索引版本与检索配置版本 |
| 未授权用户触发摄取或索引切换 | 第二版先增加维护者授权，后端每个写操作独立校验 |
| Web 重启导致摄取任务和取消状态丢失 | 长任务交给独立 worker，状态与事件持久化，不复用进程内队列作为事实来源 |
| 不可变索引版本持续占用磁盘 | 首版报告磁盘占用且不自动清理；后续单独设计经确认的保留策略 |

## 11. 推荐开发批次

- 批次 A：P00-P01，冻结文档、领域契约和 fixture 规范。
- 批次 B1：P01S 与 P02/P03/P04/P08 并行；spike 冻结解析/OCR 默认路径与 fallback，其余任务实现不依赖该选型的能力。
- 批次 B2：P05/P06 在 P01S 后并行，随后完成 P07。
- 批次 C：P09-P10，统一分块和索引。
- 批次 D：P11-P12，接入现有运行链。
- 批次 E：P13-P14，评测、部署和文档收口。
- 第二版批次 F：在首版字段和深模块 interface 稳定后，接入 RAG 评测工作台、运行历史和索引版本发布。

每个批次独立评审，避免把所有解析、索引和运行时改动堆成一个不可审查的大提交。
