# 多模态知识摄取技术调研

调研日期：2026-07-15  
对齐日期：2026-07-16  
状态：与[多模态知识摄取开发规划](./多模态知识摄取开发规划.md) v1.0 对齐  
范围：PDF、常见图片、TXT、Markdown、CSV、XLSX 知识源进入当前纯文本 Chroma RAG 链路的摄取方案。本调研为配套选型依据，架构决定见 [ADR-0001](../../../docs/adr/0001-textualize-multimodal-knowledge-before-retrieval.md)。

## 结论摘要

首版采用“多模态资料解析为可追溯的结构化文本片段，再复用现有文本嵌入、Chroma 检索和 RAG 评测”的方案。图片、表格、公式、图表和因果图不会直接写入原生图像向量。

1. 对外只保留一个深模块接口：`KnowledgeBaseMaintenance.execute(MaintenanceCommand) -> MaintenanceResult`。CLI 和第二版页面的 HTTP adapter 都调用该接口；Docling、PaddleOCR、PyMuPDF、视觉模型和 Chroma 的对象只存在于模块内部。
2. TXT、Markdown、CSV、XLSX 使用轻量、确定性的解析路径，以精确保留标题、工作表、表头、行列范围和来源定位。
3. PDF 与图片的默认生产路径不在调研阶段预判。P01S 技术 spike 必须在同一 fixture 上比较 Docling、PaddleOCR PP-StructureV3 和 PyMuPDF 基线，再固定一个默认路径和一个显式 fallback。
4. 本地 OCR 是基础能力；CPU 是所有开发者都能使用的基线，GPU 仅用于可选加速或本地视觉模型。两种设备路径必须输出相同的公共数据契约和报告结构。
5. 远程视觉描述默认关闭，只有显式允许资料外发时才能启用，并必须受调用次数硬上限约束。只有 adapter 已验证价格和币种契约时，才展示货币预算。
6. OCR 不能替代结构表达。表格要保留行列语义；因果图要保留节点、有向边和条件。无法可靠判断边方向时进入人工复核，不生成可发布的猜测结果。
7. 每次发布构建一个完整、不可变的知识库快照，不向当前非空 collection 追加或 upsert。活动版本由按 profile 管理的原子注册表切换，旧快照保留用于回滚，首版不自动删除。
8. 首版仅向开发者或维护者提供 CLI，不新增管理页面和数据库表；第二版接入现有 `/rag_eval` 页面，但页面只是同一深模块的 HTTP adapter。

## 已确认的产品与架构约束

- 资料由开发者上传，默认属于现有共享因果知识库；资料不敏感，不包含医疗隐私，也不开放给普通用户上传。
- `default`、`medical` 表示语料域和运行配置，不表示文件模态。首版只扩展 `default`；`medical` 继续使用现有 PubMedQA JSONL 构建路径。
- 首版格式固定为 TXT、Markdown、CSV、XLSX、PDF、PNG、JPG/JPEG、WebP、TIF/TIFF。DOC/DOCX、PPT/PPTX、XLS、SVG、音视频、压缩包和加密 PDF 不在范围内。
- 临时 `--source` 只用于检查或试跑，默认不能发布。发布单元是 profile 配置的完整、权威 source root 快照，不做增量 append/upsert。
- `source_id` 表示逻辑资料，文件内容变化不改变它；`source_version_id` 绑定内容哈希；`fragment_id` 还绑定定位、内容类型、提取器指纹和规范化文本哈希。
- 页码和行列范围使用从 1 开始的闭区间；图片 bbox 归一化到左上角为原点的 `[0,1]` 坐标，并保留原始宽高。
- `index_version` 是独立 persist directory/collection 中的完整不可变快照。注册表只保存相对版本根目录的路径，保证 Windows CLI 与 Docker worker 读取同一含义。
- 默认因果 benchmark 与 medical/PubMedQA benchmark 必须隔离；发布报告必须绑定相同的索引版本、benchmark、检索配置和 embedding 指纹。

## 候选能力对比

| 候选 | 官方能力 | 本地/远程 | 对当前仓库的优点 | 主要风险 | 建议角色 |
|---|---|---|---|---|---|
| Docling | PDF、Office、CSV、Markdown、图片；版面、OCR、表格、图片描述、图表、统一文档表示 | 可本地，也有服务化方案 | 一个内部 adapter 可覆盖复杂 PDF/图片，并导出 Markdown、JSON 或 chunks | 模型体积、CPU 时延、依赖冲突；不同 enrichment 需要额外模型；模型许可证需逐项核对 | 主解析候选，进入 P01S |
| PyMuPDF | 文本 blocks/words/dict+bbox、`find_tables()`、Markdown 表格 | 本地 | 仓库已经依赖；数字 PDF 路径改动小，适合作为可解释基线 | 阅读顺序和复杂表格仍需处理；扫描件需另接 OCR；AGPL/商业许可需确认 | 数字 PDF 基线或 fallback |
| PaddleOCR PP-StructureV3 | 中英文 OCR、方向/矫正、版面、表格、公式、图表、Markdown/JSON | 本地或官方 API | 中文扫描件和复杂页面能力较完整，结果包含页面和结构信息 | PaddlePaddle/Transformers/ONNX 运行时较重；CPU/GPU 差异、模型下载和容器体积 | 中文 OCR/复杂页面候选，进入 P01S |
| OpenAI-compatible vision | 图片输入生成文字描述 | 远程，取决于兼容服务 | 可补充流程图、统计图和普通图片中 OCR 无法表达的语义 | 数据外发、费用、限流、非确定性；兼容服务未必支持图片 | 显式启用的可选 adapter |
| Chroma 1.x | 文档、embedding、ID、metadata、add/update/upsert | 本地或服务端 | 可继续承载统一文本片段；现有查询和评测链路可复用 | upsert 不能提供完整快照、原子发布、已删源清理和 embedding 迁移语义 | 每版本独立目录/collection，由活动注册表发布 |

## 一手资料事实

### Docling

- 官方支持 PDF、DOCX、XLSX、PPTX、Markdown、CSV、PNG、JPEG、TIFF、BMP、WebP 等输入，并能导出 Markdown、JSON、Text 和 chunks JSONL。[支持格式](https://docling-project.github.io/docling/usage/supported_formats/)
- CLI 暴露 OCR、强制 OCR、OCR engine/language、表格 fast/accurate、图片描述和图表抽取等开关；远程服务需要显式启用。[CLI reference](https://docling-project.github.io/docling/reference/cli/)
- 官方 full-page OCR 示例支持 Tesseract、EasyOCR、RapidOCR 等后端，并提示强制全页 OCR 通常比混合检测慢。[Full page OCR](https://docling-project.github.io/docling/_generated/examples/full_page_ocr/)
- Docling 代码仓库使用 MIT 许可证；模型和外部 OCR backend 仍需分别核对许可证。[Docling repository](https://github.com/docling-project/docling)

### PyMuPDF

- `Page.get_text()` 可以输出包含位置的 blocks、words、dict；简单纯文字提取不保证自然阅读顺序。[文字提取说明](https://pymupdf.readthedocs.io/en/latest/recipes-text.html)
- `Page.find_tables()` 返回表格 bbox、行列和 cell，并可输出 Markdown 或 pandas DataFrame；无边框或非常规表格仍可能需要策略调整。[Page table API](https://pymupdf.readthedocs.io/en/latest/page.html)
- PyMuPDF/PyMuPDF4LLM 使用 AGPL 或商业许可。当前仓库已依赖它，这不是本功能新引入的风险，但扩大生产用途前仍须确认合规方式。[许可 FAQ](https://pymupdf.readthedocs.io/en/latest/faq/index.html)

### PaddleOCR

- PP-StructureV3 将版面分析、OCR、表格、公式和图表等结果转换为结构化数据，并支持 Markdown/JSON 输出。[管线教程](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html)
- 3.x 安装需要选择 PaddlePaddle、Transformers 或其他推理路径；完整文档解析需要可选依赖，不能仅根据单包安装成功推断 Windows 和 Docker 可运行。[Quick Start](https://www.paddleocr.ai/latest/en/quick_start.html)、[安装说明](https://www.paddleocr.ai/main/en/version3.x/installation.html)
- PaddleOCR 仓库使用 Apache-2.0；具体模型和依赖仍应在锁版本时记录。[PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)

### Chroma

- collection 中每条记录使用唯一字符串 ID；官方支持 `add`、`update` 和 `upsert`，文档可以由 collection embedding function 生成向量或直接附带 embedding。[Adding data](https://docs.trychroma.com/docs/collections/add-data)、[Upsert records](https://docs.trychroma.com/reference/chroma-api/record/upsert-records)
- metadata 支持字符串、整数、浮点、布尔和同类型数组。来源定位应保存为扁平字段，复杂对象额外序列化为 JSON 字符串。[Adding data](https://docs.trychroma.com/docs/collections/add-data)、[Metadata filtering](https://docs.trychroma.com/docs/querying-collections/metadata-filtering)
- collection 可独立创建和管理，删除 collection 会删除其中全部记录。[Manage collections](https://docs.trychroma.com/docs/collections/manage-collections)
- 上述能力只说明 Chroma 能存储版本数据，不提供本项目所需的跨目录原子发布协议。因此本项目采用完整不可变快照和外部活动注册表；发布失败不修改活动指针，异常恢复不自动删除任何现有索引。

### 远程视觉模型

- OpenAI Responses API 的正式接口支持 `input_image`，可使用 URL、文件 ID 或 base64 data URL；这证明视觉描述 adapter 可以通过标准图片输入实现。[Images and vision](https://developers.openai.com/api/docs/guides/images-vision)
- 图片和文件输入存在数据处理与保留约束，不能把“OpenAI-compatible”理解为任意供应商都具有相同隐私规则。[OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data#default-usage-policies-by-endpoint)
- 当前项目的文本模型 `BASE_URL`/`MODEL` 配置不能证明后端支持图片。视觉 adapter 需要独立能力探测和独立配置，不能静默复用现有回答模型。

## P01S 技术 spike 设计

在修改生产摄取路径前，使用同一组无敏感 fixture 比较三条路径：

1. Docling：数字、扫描和混合 PDF，以及中文图片、跨页表格、公式、统计图、流程图和因果图。
2. PaddleOCR PP-StructureV3：对同一组扫描和复杂页面记录相同指标。
3. PyMuPDF：数字 PDF 使用 blocks、bbox 和 `find_tables()`，作为质量、耗时和依赖成本基线。

每次运行都记录工具/模型版本、许可证、设备、操作系统、容器镜像、首次模型下载、峰值内存、每页时延和失败类型。CPU 是必测基线；有 GPU 时追加同 fixture 加速结果，但设备类型不进入 embedding 指纹。

质量必须和人工 gold 比较，至少覆盖：定位完整率、OCR 字符正确率、表格数值与行列关系、公式保真、因果节点/有向边/条件 F1、重复片段率。初始候选门槛是 locator 100%、表格数值正确率不低于 95%、OCR `1-CER` 不低于 95%、因果边 F1 不低于 95%；这些门槛和吞吐目标必须在 P01S/P13 后按冻结的 benchmark 环境确认。

P01S 的唯一选型输出是：一个默认生产路径、一个触发条件明确的 fallback，以及不支持样例的失败策略。没有实测结果前，不在规划中把 Docling 或 PaddleOCR 写成既定实现。

## 对开发任务的影响

- P01S 先冻结 fixture、指标和 benchmark 环境，再决定 P06/P07 的默认解析/OCR 路径。
- P05 只定义 `MaintenanceCommand`、`MaintenanceResult`、`KnowledgeFragment` 和报告契约；任何候选工具的原始类型都不能穿过深模块接口。
- P06/P07 实现一个默认路径和一个显式 fallback，禁止两个解析器同时生成可发布的重复片段。
- P08 的视觉描述必须独立配置、默认关闭、显式允许数据外发、缓存结果并设置调用次数硬上限；测试使用 fake adapter。
- P10 按权威 source root 构建完整不可变快照。稳定 ID 用于审计、重复检测和可复现，不用于向活动 collection 增量 append/upsert。
- P11 只实现维护者 CLI，并通过同一深模块完成 inspect、ingest、evaluate、publish、status 和 rollback；临时 `--source` 默认不可发布。
- P12 让 CLI、Web、worker 通过统一 resolver 读取活动注册表。临时 smoke 只有同时提供 `RAG_VECTOR_DB_DIR` 与 `RAG_COLLECTION_NAME` 才能覆盖注册表。
- P13 将摄取质量、检索质量和回归质量绑定到确切 index version、benchmark、检索配置及 embedding 指纹，禁止 default 与 medical/PubMedQA 交叉评测。
- P14 记录解析/OCR/模型许可证和离线部署要求，并修正生产 compose 的知识库挂载与 worker 缺口；不得改写或清理现有 `Agent/knowledge_base/db/`。
- 第二版页面不得 shell out CLI，也不得以页面进程内线程作为长任务执行源；应增加独立 worker 和持久化 run/event 模型，并复用现有任务模式而不是复用绑定 user/session 语义的 `analysis_jobs` 表。
- 第二版的 `/rag_eval` 页面与全部相关接口先做登录校验，摄取、评测、发布和回滚再做维护者授权；索引版本发布与现有检索配置发布保持两个独立动作。

## 暂不推荐

- 把 Docling、Unstructured 或 PaddleOCR 原始对象传入查询链路：这会放大接口并让检索依赖解析器实现。
- 对所有 PDF 强制 OCR：数字 PDF 会变慢，也可能降低已有文字质量。
- 只用视觉模型描述表格或因果图：数值、行列关系和边方向不够稳定，必须优先使用结构解析。
- 直接对当前非空 collection 执行 `--allow-append` 或 upsert：无法可靠处理源删除、完整发布、配置变化和中途失败。
- 在同一 persist 目录内通过重命名 collection 模拟版本发布：不能满足跨进程、跨运行环境和失败恢复所需的明确事务语义。
- 因 Chroma 支持 image 字段就改为原生图片向量：当前用户查询、embedding、rerank、证据和评测仍是文字链路，收益与复杂度不匹配。
- 让第二版页面复制摄取逻辑或直接调用 CLI 子进程：这会形成第二套行为和难以测试的进程协议。
